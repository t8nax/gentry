# Справочник по формату флоу

Флоу проекта задаёт, как агент ведёт задачи проекта. Сценарий — путь задачи, этап — шаг этого пути, фрагмент — текст, общий для нескольких этапов, субагент — агент в отдельной сессии со своей инструкцией: он выполняет этап или часть работы этапа. Флоу и общие субагенты хранятся файлами в репозитории процесса оператора. Изменения файлов — черновик; действующими они становятся после применения.

Разделы: Раскладка · Сценарий · Этап · Фрагмент · Субагент · Проверка и применение · Чего нет в этой версии · После применения.

## Раскладка

    <процесс>/
      agents/                    — общие субагенты, доступные флоу всех проектов
        reviewer.yaml
        reviewer.md
      conflict/                  — версии файлов общих субагентов с другой машины, только при конфликте
      <проект>/
        flow/                    — флоу проекта
          scenarios/             — сценарии
            feature.yaml
          stages/                — этапы: поля и инструкция
            review.yaml
            review.md
          parts/                 — фрагменты
            review-checklist.md
          agents/                — субагенты проекта
            auditor.yaml
            auditor.md
        conflict/                — версии файлов флоу с другой машины, только при конфликте
        changes.md               — файл изменений, только пока есть черновик

- Папку флоу называет flow_show в строке «Папка флоу». Папка процесса находится на два уровня выше папки флоу; общие субагенты — папка agents/ в ней.
- Имя файла без расширения — идентификатор объекта: до 64 строчных латинских букв, цифр и дефисов, первая — буква. Отображаемое название задаёт поле title.
- Этап и субагент — пара файлов с одним именем: поля в .yaml, инструкция в .md. Файл без пары — ошибка.
- Других файлов и папок во флоу быть не должно. Файлы и папки, имя которых начинается с точки, не рассматриваются.
- Файл flow.yaml предназначен для общих правил флоу. Поддерживаемых полей в нём в этой версии Gentry нет, поэтому файл не создаётся.

## Сценарий

Сценарий — направленный граф. Узел — место этапа на пути задачи, переход — ребро от узла к узлу. Сценарий задачи выбирает оператор при её взятии.

    # scenarios/feature.yaml
    title: Фича
    start: branch
    nodes:
      branch:          { stage: branch, next: plan }
      plan:            { stage: plan-feature, next: implementation }
      implementation:  { stage: implementation, next: review }
      review:
        stage: review
        next:
          - to: implementation
            if: ревью выявило существенные замечания
            max_rounds: 3
          - to: merge
      merge:           { stage: merge, next: finish }

Поля сценария, все обязательны:

- title — название сценария;
- start — начальный узел;
- nodes — узлы в порядке пути; ключ — идентификатор узла.

Поля узла, оба обязательны:

- stage — этап узла. Один этап может стоять в нескольких узлах и в нескольких сценариях;
- next — переходы. Единственный переход без условия записывается идентификатором узла: next: review. Иначе — списком переходов с полями to — узел, if — условие, max_rounds — предел возвратов.

finish — цель перехода, которым сценарий заканчивается. Узел с этим идентификатором создать нельзя.

Правила графа:

- Каждый узел достижим из начального, и из каждого узла есть путь до finish.
- У узла не более одного перехода без условия; он задаёт путь по умолчанию. Если все переходы узла имеют условия, узел — развилка.
- Два перехода одного узла к одному и тому же узлу недопустимы.
- Переход к узлу, пройденному раньше, замыкает цикл возврата. В каждом цикле должен быть переход с max_rounds или переход с условием из узла, этап которого исполняет operator: возврат, который решает оператор, может быть без предела. Предел ставится только на переход с условием и только на тот, который замыкает цикл.
- Условие записывается полным утверждением, которое агент может проверить: «ревью выявило существенные замечания», а не «замечания».

Как сценарий работает в задаче:

- Условие перехода оценивает агент и записывает обоснование. На развилке переход и обоснование обязательны, для единственного перехода с условием обоснование тоже обязательно.
- max_rounds — предел возвратов по переходу. При значении 3 возврат возможен трижды, четвёртый Gentry отклоняет. Оператор может разрешить ещё один возврат своим решением. Возврат без max_rounds Gentry не ограничивает, и разрешение для него не нужно.
- Возврат по внешнему циклу обнуляет счётчики вложенных циклов.

## Этап

Этап описывается один раз и используется в любых сценариях проекта.

    # stages/review.yaml
    title: Ревью
    exit: замечания ревью записаны и разобраны
    executor: reviewer
    include: [review-checklist]

    # stages/plan.yaml
    title: План
    exit: план согласован с оператором
    executor: orchestrator
    agents: [scout]

Поля этапа:

- title — название этапа; обязательно.
- exit — выход: результат, после которого этап закрывается; обязательно.
- executor — исполнитель; обязательно. orchestrator — основная сессия агента, operator — оператор, иначе — идентификатор субагента проекта или общего субагента.
- include — список фрагментов, которые добавляются к инструкции этапа в порядке списка; необязательно.
- agents — субагенты, которые выполняют части работы этапа по его инструкции: список идентификаторов субагентов проекта или общих субагентов без повторов; необязательно. Допустимо только у этапа с исполнителем orchestrator или operator: субагент других субагентов не запускает.
- checks — список команд проверки; необязательно. Этап закрывается выходом, только если все команды завершились успешно.
- timeout — время на все команды проверки этапа вместе: целые числа с единицами h, m, s, например 90s, 20m, 1h30m; необязательно, по умолчанию 10m.

Выход описывает проверяемый результат: что существует или выполнено, когда этап закончен. Например, «тесты проходят, изменения закоммичены в ветку задачи», а не «реализация». Агент закрывает этап выходом, когда все шаги этапа выполнены или сняты. Этап с исполнителем operator шагов не требует; закрыть его может и оператор, и агент.

Этап ведёт основная сессия: читает этап, объявляет и отмечает шаги, пишет заметки и закрывает этап выходом. Работу этапа делает исполнитель: основная сессия, оператор или субагент, которому основная сессия передаёт инструкцию этапа. Субагенты из поля agents выполняют части работы; когда и как их запускать, говорит инструкция этапа. Субагент с возможностью progress может отмечать шаги и писать заметки.

Инструкция этапа — файл .md любой длины: что сделать на этапе, в каком порядке и что считать готовым. Агент получает инструкцию только текущего этапа, поэтому инструкция не должна опираться на текст других этапов; общее выносится во фрагмент.

    <!-- stages/review.md -->
    Проверить изменения задачи: поведение, тесты и тексты для оператора.
    Каждое замечание записать с местом и важностью.

### Команды проверки

Когда агент закрывает этап выходом, Gentry выполняет команды из checks по порядку в рабочей копии задачи. Если команда завершилась с ненулевым кодом или команды не уложились во время timeout, выход отклоняется, а остальные команды не выполняются. Успех команды Gentry определяет только по коду выхода: 0 — команда прошла. Отказ называет команду, код выхода и путь к файлу с полным выводом команды, а затем передаёт последние 100 строк вывода без изменений. Пропуск этапа команды не выполняет.

    # stages/implementation.yaml
    title: Реализация
    exit: код и тесты написаны, тесты проходят
    executor: coder
    checks:
      - go vet ./...
      - go test ./...
    timeout: 20m

Команда выполняется без оболочки: Gentry делит строку на программу и аргументы по пробелам, аргумент с пробелами заключается в одинарные или двойные кавычки. Символы оболочки |, &&, >, $ и * не действуют. Если оболочка нужна, команда вызывает её сама, например sh -c "go test ./... | tee test.log". Команды записываются по одной в строке, как в примере: в записи в квадратных скобках запятая внутри команды разделила бы её на две.

## Фрагмент

Фрагмент — файл parts/<идентификатор>.md с текстом, общим для нескольких этапов: например, формат плана или список проверки ревью. Этап подключает фрагмент полем include; агент получает текст фрагмента после инструкции этапа. Фрагмент, на который не ссылается ни один этап, допустим.

## Субагент

Субагент работает в отдельной сессии со своей инструкцией и своими возможностями: выполняет этап как исполнитель или часть работы этапа, который называет его в поле agents.

    # agents/reviewer.yaml
    purpose: ревью изменений задачи — поведение и текст
    capabilities: [read, search]
    model: strong

Поля субагента:

- purpose — назначение одной строкой; обязательное поле.
- capabilities — список возможностей из read, search, edit, run, web, task, progress; обязательное поле. Без task и progress субагенту недоступны инструменты Gentry: результат он возвращает основной сессии, которая его записывает.
  - task — видеть задачу: этап, постановку и решения оператора, заметки.
  - progress — видеть задачу и вести ход работы: шаги, заметки, артефакты. Закрывает этап и записывает решения оператора основная сессия.
- model — модель субагента: light, standard или strong; необязательное поле. Без него субагент работает на модели основной сессии. Модель ИИ-инструмента для каждого значения выбирает Gentry.
  - light — простая и быстрая работа, например поиск по коду.
  - standard — обычная работа.
  - strong — работа, где важна точность суждений, например ревью.

Инструкция субагента — файл .md: что субагент делает, что возвращает и чего не делает.

Где хранится субагент:

- Субагент проекта лежит в папке agents/ флоу. Субагент проекта заменяет одноимённого общего субагента.
- Общий субагент лежит в папке agents/ процесса и доступен флоу всех проектов.

Этап называет субагента, если субагент — его исполнитель или стоит в его поле agents. Общий субагент входит во флоу проекта и раскладывается в рабочие копии, только если его называет этап проекта.

Субагенты обоих видов — часть черновика флоу: flow_apply применяет их вместе с флоу проекта.

Чтобы сделать субагента проекта общим, нужно создать его пару файлов в папке общих субагентов, удалить пару из флоу и применить черновик.

Изменение общего субагента затрагивает все проекты, этапы которых его называют, и применяется из любого проекта. Если изменение вносит ошибку в действующий флоу другого проекта, flow_apply его не применяет; если применение прошло, flow_apply называет другие проекты, затронутые изменением.

## Проверка и применение

- flow_show с полем draft показывает черновик флоу вместе с изменениями общих субагентов, а если в нём есть ошибки, — их перечень. Каждая ошибка называет объект: сценарий, узел, этап, фрагмент или субагента.
- flow_diff выводит сводку изменений флоу проекта и общих субагентов и формирует файл изменений changes.md со схемами сценариев и полными текстами изменённых объектов. Файл удаляется при применении, отмене черновика и синхронизации, принёсшей изменения. Файл и папку conflict/ агент не изменяет.
- flow_apply проверяет черновик флоу проекта и общих субагентов и делает его действующим. Черновик с ошибками не применяется.
- flow_discard возвращает папку флоу и папку общих субагентов к действующему виду; изменения черновика теряются.
- Коммиты в репозиторий процесса делает только Gentry.

При применении Gentry проверяет: пары файлов; обязательные поля и их значения; идентификаторы; ссылки на этапы, фрагменты и субагентов; граф каждого сценария; наличие хотя бы одного сценария; отсутствие лишних файлов.

## Чего нет в этой версии

Поля on_take, on_close, on_cancel в flow.yaml и сценарии, а также on_enter, on_exit и procedures в этапе — действия в трекере и процедуры знания — появятся в следующих версиях. Сейчас Gentry отклоняет флоу с этими полями. Если этапу нужно действие в трекере, оно описывается словами в инструкции этапа.

## После применения

- Новые задачи идут по действующему флоу. Задача сохраняет снимок флоу при взятии, поэтому задачи, взятые раньше, продолжают идти по прежнему флоу.
- Если подключён удалённый репозиторий процесса, Gentry отправляет применённые изменения на другие машины.
- Если другая машина изменила тот же флоу или тех же общих субагентов, Gentry отклоняет применение. Изменения этой машины остаются черновиком, версии спорных файлов другой машины лежат в папке conflict/, а отказ называет эту папку. Следующее применение принимает черновик; применение или отмена черновика удаляет папку conflict/.
